### Алгоритм и приоритеты (PHP 7.4–8.2, целевой default 8.2)

Разбор остаётся рекурсивным descent по токенам Unit с учётом `pairs`. Бинарные операторы выбираются по минимальному приоритету вне скобок; при равном приоритете — самый правый оператор для right-assoc (`=`, составные присваивания, `??`) и самый левый для left-assoc. Приоритеты от слабого к сильному:

1. `or`
2. `xor`
3. `and`
4. `=` / `+=` / `-=` / `*=` / `/=` / `.=` / `%=` / `??=` (right)
5. тернарный `? :` и сокращённый `?:` (left; вложенный `:` ищется с учётом вложенных пар)
6. `??` (right)
7. `||`
8. `&&`
9. сравнения `==` `!=` `===` `!==` `<` `>` `<=` `>=`
10. `.` `+` `-`
11. `*` `/` `%`

Префиксы после выбора бинарного корня: `!` `-` `+` `clone` `throw` и приведение `(T)E`, где `T` ∈ {`int`,`integer`,`bool`,`boolean`,`float`,`double`,`real`,`string`,`array`,`object`,`unset`}. Постфиксы первичного выражения: вызов `()`, доступ `->`/`?->`/`::`, индекс `[]`. Группирующие скобки без имени типа по-прежнему снимаются целиком.

Структурные узлы AST: `Cast`, `Ternary` (`then` отсутствует у `?:`), `Index`, `CompoundAssign`, `Array` с опциональным ключом элемента. Неизвестный остаток оформляется одним `Unknown` с сохранёнными известными детьми; повторное дробление по служебным токенам не заменяет разбор поддерживаемых конструкций.

### Потребление и диагностики

`flow.rs` обходит новые узлы: сохраняет вложенные вызовы/чтения/записи; для ветвей тернарного добавляет условие ветки; левый операнд `?:` учитывается один раз; тип `(int)/(bool)/(string)/(object)` берётся из операции без исполнения PHP. Неизвестный receiver/target остаётся unresolved. `analysis_limitation` выдаётся один раз на корневой `Unknown` конструкции; вложенные `Unknown` той же конструкции не каскадируют отдельные сообщения для `::`/`->`/`:`/фрагментов. Независимые ограничения одной строки остаются различимыми. Yii2 не восстанавливает разрушенную PHP-цепочку; отсутствие vendor-определений не маскируется грамматикой. Syntax error по INDEX-04 по-прежнему инвалидирует файл. Приёмка — регрессии графа в `tests/native_php.rs` и сценарии PLUGIN-05–PLUGIN-07.

## Ограниченный параллелизм индексации (2026-11-04)

Запрос владельца: использовать несколько потоков для индексации. Сейчас HTTP runtime и watcher уже разделены по потокам, но PHP parse и Git provenance выполняются последовательно. Один процесс Atlas сохраняется; внутри независимых стадий используются настоящие рабочие потоки Rust, без запуска PHP или дочерних индексаторов.

- Конфигурация: `ATLAS_INDEX_WORKERS`, необязательное целое 0..32, default 0. Ноль выбирает ceil(ATLAS_CPU_LIMIT), ограниченный 1..32; положительное значение задаёт верхний предел рабочих потоков стадии. При N задачах запускается не больше min(N, workers); значение 1 сохраняет последовательный режим. Оба consumer Compose передают переменную при старте. CPU quota контейнера задаётся отдельно ATLAS_CPU_LIMIT; одни дополнительные потоки quota не увеличивают. Дополнительных ограничений памяти по непроверенной формуле не вводится.
- Общий scoped worker pool распределяет существующие элементы среза через короткую блокировку итератора, без копии входных файлов/графа на каждый поток и без неограниченной очереди заданий. Каждый слот имеет единственного писателя. Первый fatal error останавливает выдачу новых заданий; все начатые потоки join до возврата. Паника worker преобразуется в ошибку всей подготовки. Компонент не зависит от HTTP, БД или PHP; это выбранный Worker Pool для независимых CPU/IO задач.
- PHP: tokenize/parse/version-check каждого файла выполняются параллельно. Результаты остаются в слотах исходного порядка; координатор последовательно переносит успешные Unit/Declarations, переназначая индексы unit/closure после пропущенных ошибочных файлов. Затем общие объявления, связи, анализ функций и Yii2 выполняются в прежнем порядке, поскольку изменяют общие семантические данные. Полные AST не клонируются на каждый worker. Обычные parse diagnostics не прекращают другие файлы; timeout/graph-limit прекращают подготовку.
- Git: перед стадией создаётся один pinned GitReader со снимком HEAD; worker получает его clone, обрабатывает свой mutable Node и его returns. Все readers используют общий ограниченный cache объектов (64 MiB/4096 entries) и pack-index (один индекс до 64 MiB) через Arc и короткие mutex; чтение/распаковка объектов и diff выполняются вне общей блокировки. Ошибка открытия Git остаётся одинаковой недоступностью истории для всех узлов. Фиксация одного HEAD исключает смешивание разных снимков между workers. Параллельные временные decode/diff buffers всё равно увеличивают RSS; старые ограничения каждого чтения сохраняются, отсутствие OOM не обещается.
- Индексатор передаёт количество workers через AnalysisOptions. Подготовка не удерживает AtlasService; завершение всех workers предшествует проверке исходников и единственной транзакции публикации. API и контракты доверия не меняются. Параллельный completion увеличивает общий счётчик внутри mutex прогресса, поэтому он не откатывается назад при out-of-order завершении. В API/UI/logs добавляются workers и active_workers; показываемый путь относится к одной текущей/последней задаче, а не ко всем потокам.
- TDD: конфигурация и Compose forwarding; фактический overlap и верхняя граница worker pool; stop/join при ошибке/панике; идентичные PHP/полные индексные результаты при 1 и 4 workers с ошибочными файлами; pinned HEAD и общий Git cache; конкурентный монотонный progress. Сохраняются проверки нативного runtime без интерпретаторов, Git loose/pack/worktree и строгий OpenSpec. Живой Docker и ускорение проекта владельца проверяются отдельно.

## Загрузка веб-модулей на внешнем порту (2026-11-04)

Пользователь сообщил `GET http://localhost:8085/assets/app.js ... 403`. В текущем HTTP adapter общий Origin guard применяется даже к публичным assets: если Origin отсутствует в ATLAS_ALLOWED_ORIGINS, JavaScript не загружается, submit-handler не устанавливается и токен не отправляется через API.

Граница ответственности исправляется в HTTP guard: выбор роли маршрута выполняется до Origin-проверки. `/mcp` и `/api/*` сохраняют существующие token/Origin ограничения; публичные HTML, CSS, JS-модули и health не зависят от reviewer-токена или списка API origins. Статика содержит только поставляемый интерфейс, без данных проекта. CORS-разрешения для API не расширяются; новые настройки и изменения Service Layer не требуются. Используется существующая граница публичных ресурсов и защищённых API без отдельной абстракции.

В текущем опубликованном образе проблему можно обойти настройкой ATLAS_HOST_PORT=8085 и ATLAS_ALLOWED_ORIGINS с явными http://localhost:8085 и http://127.0.0.1:8085, переданными через Compose environment, затем пересозданием контейнера. Это также необходимо для защищённых запросов с Origin после загрузки страницы. Не выводить правильность токена из ошибки загрузки JS: он ещё не был проверен. TDD: GET всех зависимостей веб-модуля с Origin внешнего порта сначала получает 403; после исправления 200 и правильный MIME. Дополнительный сценарий подтверждает сохранение 403/401 для API и успех разрешённого origin с reviewer token.

## Прогресс индексации (2026-11-04)

Запрос владельца: видеть ход индексации и понимать оставшееся время. До изменения runtime сообщал только готовый результат.

- Service Layer владеет отдельным `IndexingProgress`: разделяемым снимком текущего запуска в памяти. Его короткая блокировка независима от блокировки AtlasService/транзакции PostgreSQL. HTTP получает handle при сборке router, поэтому `/api/indexing` отвечает даже при сохранении большого графа. Доступ требует существующий reviewer token; ответы не кэшируются. После перезапуска состояние снова waiting, прошлый запуск не объявляется успешным.
- IndexCoordinator управляет жизненным циклом waiting → running → completed/failed и стадиями discovery, reading, analysis, git, validation, publishing. Плагины получают progress reporter через AnalysisOptions, сообщают подэтап и фактически обработанные единицы; транспорт и БД им неизвестны. Для независимого наблюдения используется разделяемая модель чтения состояния, без очереди событий и хранения исходников. Прямой `index` и watcher используют один контракт. Ошибка подготовки/публикации сохраняет стадию и ошибку; completed выставляется только после успешного commit.
- Снимок содержит run_id, state, stage, detail, completed, total (nullable), unit, current_path, elapsed_ms, stage_elapsed_ms, eta_seconds (nullable), error. Процент относится только к текущему подэтапу. Оценка оставшегося времени = среднее время завершённой единицы × оставшиеся единицы; появляется после ≥3 единиц и ≥1 секунды. Изменение этапа сбрасывает оценку. При неизвестном объёме работ, ошибке или недостатке наблюдений ETA отсутствует. Общий ETA по числу файлов не вычисляется: Git/анализ/commit имеют разную стоимость. Завершённое время замораживается.
- Веб-панель над вкладками показывает стадию, текущий файл, счётчик, progressbar, прошедшее время и явно подписанный ETA этапа. Неизвестный объём отображается неопределённым progressbar. Опрос запускается после ввода токена независимо от аналитики, выполняется последовательно с timeout 10 секунд и возобновляется после сетевой ошибки; потеря связи скрывает устаревшие проценты/ETA. Частота берётся из существующего ATLAS_POLL_MS (default 1000 ms, тип и валидация остаются в Config); API сообщает poll_interval_ms, веб ограничивает частоту минимумом 250 мс. В CLI/Docker stderr выводятся переходы этапов и продвижение по десяткам процентов не чаще раза в секунду; при медленном этапе следующее событие после пяти секунд выводится независимо от процента. Переход и терминальный результат выводятся сразу. stdout команды index остаётся JSON.
- Проверки: наблюдаемая red-фаза для API авторизации/чтения при занятом сервисе, полного цикла/ошибки/retry индексатора и UI-представления; затем реализация, Rust/Node, форматирование/Clippy и strict OpenSpec. Живой браузер, Docker и PostgreSQL отмечаются отдельно от in-process проверок.

## Context

Реализация начата по запросу владельца после ТЗ v0.3. Ниже записаны инженерные решения этого этапа; это новые решения реализации, а не утверждение, что они ранее были выбраны владельцем. См. [proposal.md](proposal.md) и [open-questions.md](open-questions.md).

Работа ведётся в отдельных Git worktree. В исходной среде запись в корневую `.git` и доступ к Docker daemon запрещены; рабочий Git находится в разрешённом временном каталоге. Подпись 1Password недоступна; служебные локальные коммиты выполняются без подписи и без изменения глобального Git config.

## Goals / Non-Goals

**Goals:** реализовать работающий вертикальный срез всех согласованных возможностей с настоящим AST, PostgreSQL, MCP, веб-проверкой и аналитикой; разделить бизнес-правила и адаптеры; проверять поведение через TDD и интеграционные сценарии.

**Non-Goals:** полный межпроцедурный анализ значений, выполнение исследуемого PHP, угадывание runtime-конфигурации Yii, обязательные эмбеддинги, утверждение о фактическом использовании агентом данных без обратной связи.

## Decisions

### Архитектура и зависимости

Основное приложение — Rust 2021. HTTP реализуется через Axum 0.7, асинхронный жизненный цикл — Tokio. По уточнению владельца v0.4 PHP-плагин и отдельный Yii2-плагин реализуются в Rust и компилируются в Atlas. Внешние PHP CLI/Composer и autoload отсутствуют. Контракт перед реализацией: [native-analyzer-design](../../../docs/native-analyzer-design.md).

Слои:

1. Domain: вершины, рёбра, доверие, ревизии, исправления, ошибки.
2. Service Layer: индексация, контекст, исправление/проверка, учёт выдачи и аналитика.
3. Repository: PostgreSQL в production и изолированный memory adapter для модульных тестов.
4. Adapters: native language/framework plugins, native Git reader, watcher, HTTP/MCP, веб-страница, ENV.

Обработчики MCP и веба вызывают сервисы. Бизнес-правила не дублируются в HTTP. Паттерны Repository и Strategy используются для хранилища и плагинов; optimistic concurrency — для предотвращения потери конкурирующих правок. Отдельная абстракция вводится только для существующей границы.

PostgreSQL adapter использует узкую RAII-обёртку над libpq с параметризованными запросами. Это позволяет использовать установленный PostgreSQL и проверять настоящий SQL без недоступной загрузки нового Rust-драйвера. Соединения и результат освобождаются автоматически. Синхронный сервис сериализует операции; HTTP не удерживает бизнес-логику. PostgreSQL хранит сущности, рёбра, исправления и выдачи отдельно с индексами.

### Общий контракт данных

`SourceSpan { path, start_line, end_line }` использует относительный путь и строки с единицы.

`Node { id, kind, name, qualified_name, span, metadata, trust, revision }`.

`Edge { id, kind, from, to: optional node id, span, metadata, trust, revision }`.

`Diagnostic { path, line, code, message }`.

`GraphSnapshot { nodes, edges, diagnostics }` — JSON-контракт анализатора. Поля trust/revision отсутствуют у входа анализатора или имеют значения 1/0; сервис задаёт фактическое доверие.

`GraphContext { root_id, nodes, edges, diagnostics, truncated }` — ограниченный связный ответ. Контекст не смешивает рёбра contains/inherits/overrides с calls. Неоднозначный вызов сохраняет кандидатов и диагностику.

### Service Layer contract

`AtlasService::new(Box<dyn Repository>)`; методы изменяют сервис через `&mut self` и возвращают типизированный `Result`:

- `index(snapshot, indexed_paths, removed_paths) -> IndexReport`;
- `search(query, limit) -> Vec<Node>`;
- `context(root_id, depth, limit) -> GraphContext`;
- `correct(target_kind, target_id, expected_revision, patch, reason) -> Correction`;
- `review(correction_id, expected_revision, approve) -> Correction`;
- `pending_reviews(limit) -> Vec<Correction>`;
- `record_delivery(response_id, node_ids, edge_ids, timestamp) -> ()`;
- `analytics(from, to, bucket_seconds) -> Analytics`.

`PostgresRepository::connect(database_url)` и `migrate()` подготавливают production-хранилище. Данные тестов не заменяют production-хранилище.

### Идентичность и доверие: Q-01–Q-08

Семантический ключ включает kind, FQN и область переменной. Сдвиг строк не меняет идентичность. Для переноса/переименования используется уникальное структурное сопоставление без позиции и имени; неоднозначность не разрешается произвольным выбором. Защищённые объекты при неоднозначном сопоставлении не удаляются через фиктивное delete/create; неопределённость видна в диагностике.

Защищаются семантические metadata и исправленная цель ребра; позиции в файле обновляются анализатором. Полное удаление подтверждается только успешным анализом соответствующей области или установленным удалением файла. Ошибка разбора не считается удалением. Настоящее удаление удаляет объект независимо от доверия.

Исправление имеет envelope `{metadata: object, to?: node-id|null}`. Поле `to` допустимо только у ребра и с существующей целью. Идентификатор, тип, источник ребра, позиции, доверие и ревизии нельзя произвольно изменить агентом.

Каждая мутация использует ожидаемую ревизию и транзакцию. Конкурирующая устаревшая правка отклоняется. `approve` подтверждает текущую правку уровнем 3. `decline` отменяет текущую правку и восстанавливает предыдущие семантические данные и доверие, сохраняя актуальные позиции; для цепочки исправлений возвращается предшествующая правка. Рассмотрение уже замещённой правки возвращает конфликт. Разработчик использует approve/decline без произвольного ввода альтернативы.

Граница атомарности — один пакет индексации или одно пользовательское действие. Ошибка откатывает весь пакет.

### Анализ PHP и Yii: Q-09, Q-11, Q-14, Q-18

Языковой плагин получает SourceFile[] и AnalysisOptions через Rust trait LanguagePlugin, возвращает GraphSnapshot. FrameworkPlugin обогащает граф; Yii2 отдельно зарегистрирован с зависимостью php. Реестр выбирает файлы по расширениям языка, а Service Layer не содержит PHP-специфичных правил. Проходы: объявления/FQN → области и возвраты → разрешение связей → Yii enrichment. Возвраты сохраняют выражение, тип каждого случая, условия, фрагмент и источники. Неизвестный тип обозначается unknown. Неявное завершение отмечается отдельно и не подменяет явные return; исключения не считаются return.

Модель включает classes/interfaces/traits/functions/methods/variables/properties и typed edges contains/calls/inherits/implements/uses_trait/overrides/available_via/reads/writes. Точный набор отражает фактически поддерживаемые конструкции и документируется вместе с тестами.

Yii-плагин раскрывает статически определимые magic getter/setter и обращения через известные компоненты/поведения. Наличие реализации интерфейса само по себе не делает её активной. Динамические данные получают диагностику. Анализ зависимостей доступен через настраиваемое включение vendor; файлы не исполняются.

### Индексация и Git: Q-12–Q-13

Watcher проверяет выбранные директории, вычисляет изменение содержимого и отсчитывает debounce от последнего изменения. Полный согласованный снимок проекта позволяет обновлять затронутые межфайловые связи. Служебные директории исключены. Пути ограничены корнем, symlink за пределы проекта не обходится. Файлы обрабатываются с пределом размера. Встроенный разбор не запускает интерпретатор; ошибка синтаксиса или неподдержанный разбор не допускает публикации частичного графа файла. Неуспешный анализ оставляет предыдущие сведения с диагностикой; он не авторизует удаления.

Git вызывается аргументами subprocess без shell-интерполяции. История использует blame для последней правки, commit metadata и diff предыдущего/текущего состояния, включая контекст метода и незакоммиченные изменения. Отсутствие Git или shallow-истории отображается как недоступность истории.

Текущий фрагмент `after` отделён от `at_commit`. Последняя правка строки (`commit/message`) и всего участка (`region_commit/region_message`) имеют отдельные поля; участок сопоставляется с HEAD по diff-hunks перед `git log -L`. Новые строки в существующем файле классифицируются по изменениям строк, а не по наличию файла у родителя. Для незакоммиченного или неоднозначно сопоставленного участка коммит не угадывается. Git cache ограничен 64 MiB/2048 командами.

### MCP, веб и аналитика: Q-10, Q-20–Q-22

HTTP `/mcp` поддерживает явно объявленную совместимую версию MCP `2025-11-25`: initialize, ping, tools/list, tools/call и notifications/initialized. GET возвращает 405; SSE не используется. Инструменты: atlas_search, atlas_context, atlas_correct. Создание/удаление и developer-решения через MCP не предоставляются.

Веб: `/`, `/health`, `/api/reviews`, `/api/reviews/{id}/decision`, `/api/analytics`, поиск и просмотр контекста. MCP-agent и reviewer используют разные настроенные токены. Origin и размер запроса проверяются на транспортной границе.

Аналитика учитывает выданный MCP-контекст, отдельно от чтения вебом и внутреннего обхода. Уникальный идентификатор выдачи предотвращает повторный учёт одного события; внутри события каждый объект считается один раз. Периоды UTC полуоткрытые [from,to), интервалы — дни. Сводка, динамика и рейтинг используют один период. После удаления объекта выдачи сохраняют его идентификационный снимок. Это не свидетельство фактического использования агентом и не измерение экономии токенов.

### ENV и развёртывание: Q-15–Q-17, Q-23

Один контейнер PostgreSQL + pgvector + Rust binary со встроенными PHP и Yii2 плагинами. Git читается нативно, без Git CLI. В runtime не устанавливаются интерпретаторы языков, Composer, компиляторы или внешние анализаторы. Данные PostgreSQL в named volume, исходный проект в read-only mount. Entry point контролирует PostgreSQL и приложение и завершает их при остановке. Процессы не подменяют исполнение исследуемого проекта.

ENV-контракт документируется в `.env.example`, README и тестах Config. Минимальный набор: ATLAS_DATABASE_URL, ATLAS_PROJECT_ROOT, ATLAS_WATCH_DIRS, ATLAS_EXCLUDE, ATLAS_DEBOUNCE_MS, ATLAS_POLL_MS, ATLAS_LANGUAGE_PLUGINS, ATLAS_FRAMEWORK_PLUGINS, ATLAS_MAX_ANALYSIS_BYTES, ATLAS_MAX_GRAPH_ELEMENTS, ATLAS_ANALYSIS_TIMEOUT_SECS, ATLAS_INCLUDE_VENDOR, ATLAS_MAX_FILE_BYTES, ATLAS_CPU_LIMIT, ATLAS_INDEX_WORKERS, ATLAS_MEMORY_LIMIT_MB, ATLAS_BIND, ATLAS_MAX_CONTEXT_NODES, ATLAS_MAX_CONTEXT_DEPTH, ATLAS_MAX_REQUEST_BYTES, ATLAS_AGENT_TOKEN, ATLAS_REVIEW_TOKEN, ATLAS_ALLOWED_ORIGINS. Списки задаются JSON-массивами, boolean — true/false, численные лимиты проверяются при запуске. Некорректные значения останавливают старт с именем параметра без раскрытия секрета. Docker limits применяются также Compose настройками ресурсов; ENV самостоятельно не является механизмом cgroups.

## Risks / Trade-offs

- Статический анализ динамичного PHP не даёт знания всех runtime-значений → явные кандидаты и диагностика, без угадывания активной реализации.
- Переименование с одновременным изменением тела неоднозначно → сохранять защищённые знания и явно показывать проблему сопоставления.
- Синхронный PostgreSQL сервис сериализует операции → простая корректность первой реализации, измерения перед добавлением параллелизма.
- Docker daemon недоступен в текущей среде → проверять реальный PostgreSQL через локальный Unix socket и Compose статически; запуск контейнера не объявлять проверенным без фактического запуска.

## Validation

До реализации каждого компонента выполняется падающий тест по ожидаемому поведению. Затем минимальная реализация и рефакторинг. Проверяются доменные переходы, SQL rollback/concurrency, AST fixtures, MCP router, ENV, Git fixtures, watcher и полный путь index → context → correction → review → analytics. Итоги и ограничения записываются в verification.md.

### Поставка образа: уточнение v0.5

Публикуемый артефакт — самостоятельный Docker-образ `drlenux/memory-tools`, default tag 0.1.0 соответствует текущему Cargo.toml. Основной Compose использует image без build; отдельный docker-compose.build.yml предназначен издателю. Самостоятельный examples/compose.atlas.yml добавляется в чужой проект без ссылок на checkout Atlas. Хостовые ATLAS_POSTGRES_* отображаются в POSTGRES_*/PG* внутри контейнера, чтобы исключить пересечение с БД приложения; volume остаётся Compose-scoped. Healthcheck и стабильные пути находятся в образе. Подробнее: [дизайн поставки](../../../docs/image-distribution-design.md) и [команды публикации](../../../docs/distribution.md).
