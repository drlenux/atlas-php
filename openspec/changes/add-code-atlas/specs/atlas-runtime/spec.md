# Развёртывание и хранение атласа

## Purpose

Определить согласованные ограничения развёртывания, хранения и обновления атласа, конфигурацию через ENV в docker-compose и возможность ограничивать потребление ресурсов.

Источник: [ТЗ](../../../../../code-atlas-specification.md), разделы 3 и 7.4. Нерешённые детали: [Q-08, Q-15, Q-16, Q-17, Q-23](../../open-questions.md).

## ADDED Requirements

### Requirement: RUNTIME-07 Загрузка публичного веб-интерфейса

Система SHALL отдавать публичные HTML, CSS и JavaScript-модули интерфейса без reviewer-токена и независимо от списка допустимых Origin защищённого API. Проверки Origin и роли токена SHALL сохраняться для `/api/*` и `/mcp`.

#### Scenario: Модуль загружается на внешнем порту

- **WHEN** браузер запрашивает `/assets/app.js` и его модули с Origin внешнего порта, отсутствующего в списке API origins
- **THEN** сервер возвращает публичные модули с HTTP 200 и корректным MIME
- **AND** обработчики интерфейса могут запуститься и показать результат подключения

#### Scenario: Защищённый запрос после загрузки интерфейса

- **WHEN** запрос к API содержит Origin, отсутствующий в ATLAS_ALLOWED_ORIGINS
- **THEN** запрос получает 403 даже с правильным токеном
- **AND** разрешённый Origin без нужного токена получает 401
- **AND** разрешённый Origin с reviewer-токеном получает состояние индексации

### Requirement: RUNTIME-01 Единый контейнер

Система SHALL развёртываться в отдельном Docker-контейнере на основе PostgreSQL с добавленным бинарником приложения и доступом к папке проекта. PostgreSQL и приложение SHALL находиться внутри одного контейнера; в PostgreSQL SHALL быть установлено расширение pgvector. Для анализа система SHALL использовать нативные расширения бинарника Atlas и SHALL NOT требовать PHP CLI, Composer или runtime других анализируемых языков. Обязательный сценарий применения pgvector не установлен.

#### Scenario: Состав развёрнутой системы

- **WHEN** система развёрнута для выбранного проекта
- **THEN** PostgreSQL и бинарник приложения находятся в одном контейнере на основе PostgreSQL
- **AND** приложение имеет доступ к папке проекта, а в PostgreSQL установлен pgvector

#### Scenario: Анализ без языкового runtime

- **WHEN** в контейнере установлены PostgreSQL/pgvector и бинарник Atlas, а PHP CLI и Composer отсутствуют
- **THEN** PHP-анализ и расширение Yii 2 выполняются внутри Atlas

### Requirement: RUNTIME-02 Хранение данных в PostgreSQL

Система SHALL хранить данные атласа в PostgreSQL с индексами, включая согласованные сведения о коде, которые пока не используются запросами. Конкретная схема таблиц и состав индексов определяются отдельно.

#### Scenario: Сохранение результата анализа

- **WHEN** анализатор успешно сохраняет сведения о сущностях и связях проекта
- **THEN** эти данные находятся в PostgreSQL и для хранения атласа предусмотрены индексы

#### Scenario: Сведения пока не запрошены агентом

- **WHEN** анализатор получает предусмотренные спецификациями сведения, которые ещё не используются запросами агента
- **THEN** эти сведения сохраняются в атласе независимо от наличия текущего запроса

### Requirement: RUNTIME-03 Транзакционные обновления

Система SHALL выполнять все обновления данных через транзакции: изменения анализатора, исправления агента и решения разработчика. Успешное обновление SHALL фиксироваться через commit; при ошибке незавершённая транзакция SHALL откатываться без частично применённого итогового состояния. Границы одной транзакции определяются отдельно.

#### Scenario: Успешная транзакция

- **WHEN** обновление от анализатора, агента или разработчика успешно завершено
- **THEN** изменения в границах этой транзакции зафиксированы через commit

#### Scenario: Ошибка во время обновления

- **WHEN** транзакция любого из трёх источников завершается ошибкой до commit
- **THEN** изменения этой незавершённой транзакции откатываются
- **AND** частично применённое обновление не становится итоговым состоянием атласа

### Requirement: RUNTIME-04 Настраиваемые ограничения ресурсов

Система SHALL предоставлять настройки допустимого использования CPU и оперативной памяти. Единицы CPU, механизм ограничений, значения и область действия — приложение или весь контейнер — определяются отдельно.

#### Scenario: Задание ресурсных ограничений

- **WHEN** оператор настраивает допустимое потребление ресурсов системы
- **THEN** доступны настройки ограничения CPU и RAM, используемые системой при работе

### Requirement: RUNTIME-05 Конфигурация через ENV в docker-compose

Система SHALL поддерживать конфигурацию всех предусмотренных настроек приложения через переменные окружения, передаваемые контейнеру в `docker-compose.yml`. Это включает директории наблюдения, исключения, задержку переиндексации, выбор языковых и фреймворковых плагинов и настройки ограничения ресурсов. При запуске приложение SHALL использовать переданные значения без необходимости изменять исходный код, пересобирать образ или вручную редактировать конфигурационные файлы внутри контейнера. Имена ENV, форматы значений, обязательность, значения по умолчанию и обработка некорректных настроек определяются отдельно.

#### Scenario: Запуск с настройками из docker-compose

- **WHEN** контейнер запускается с корректными ENV настроек приложения, заданными через docker-compose
- **THEN** приложение использует переданные значения для соответствующих настроек
- **AND** ручное редактирование конфигурационных файлов внутри контейнера не требуется

#### Scenario: Изменение конфигурации без пересборки

- **WHEN** оператор изменил значения ENV в docker-compose и запустил контейнер с обновлённым окружением и прежним образом
- **THEN** приложение использует новые значения
- **AND** изменение исходного кода и пересборка образа для применения этих настроек не требуются

### Requirement: RUNTIME-06 Поставка готового образа

Система SHALL собираться как самостоятельный Docker-образ, публикуемый в registry. Проект-получатель SHALL подключать Atlas добавлением сервиса с image, ENV, read-only mount исходников и отдельным named volume в свой Compose без исходников Atlas, Dockerfile и локальной сборки. Runtime-пароли и токены SHALL задаваться при запуске, не в образе. Рецепт сборки издателя SHALL быть отделён от конфигурации получателя.

#### Scenario: Подключение к чужому проекту

- **WHEN** в Compose другого проекта добавлен сервис с опубликованным образом Atlas и настройками
- **THEN** pull и up используют этот образ без локального build и файлов из репозитория Atlas
- **AND** PostgreSQL/pgvector, бинарник, плагины, веб и механизм запуска поставляются в образе

#### Scenario: Независимая БД атласа

- **WHEN** проект-получатель уже имеет собственные POSTGRES_* переменные и сервис БД
- **THEN** Atlas использует явно заданные ATLAS_POSTGRES_* и собственный volume
- **AND** пароль и параметры БД приложения не подхватываются как неявные настройки Atlas

#### Scenario: Обновление версии образа

- **WHEN** получатель меняет тег или digest, выполняет pull и пересоздаёт только сервис Atlas с прежним volume
- **THEN** новая версия использует сохранённые данные атласа без локальной сборки
- **AND** миграция между major-версиями PostgreSQL рассматривается отдельно от обычной замены приложения
