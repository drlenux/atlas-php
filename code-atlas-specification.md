# Атлас кода с MCP-доступом

Техническая спецификация требований · версия 0.5 · 4 ноября 2026 года

Изменения версии 0.5: сборка и публикация готового Docker-образа в drlenux/memory-tools; установка в чужой проект через image в его Compose без исходников Atlas и локального build.

Изменения версии 0.4: плагин — нативное расширение анализатора внутри Atlas, а не программа на анализируемом языке. PHP и Yii 2 — два отдельных плагина; runtime-поставка содержит PostgreSQL/pgvector и бинарник Atlas без интерпретаторов языков проекта. Предусмотрено расширение на JavaScript, Go, Rust и Python.

Изменения версии 0.3: конфигурация приложения задаётся переменными окружения через docker-compose.

Изменения версии 0.2: добавлены приоритеты подходов к реализации и веб-аналитика использования данных графа по последующему уточнению владельца.

## 1. Статус и границы документа

Документ фиксирует требования владельца проекта из обсуждения и последующих уточнений. Это спецификация системы, а не описание уже реализованного продукта.

Последние уточнения имеют приоритет: отношения представлены типизированными рёбрами, а не отдельными вершинами; хранение — PostgreSQL с установленным pgvector внутри одного Docker-контейнера вместе с приложением; исправления подчиняются трём уровням доверия.

В документе различаются:

- **Требование** — прямо высказанное или подтверждённое владельцем поведение.
- **Предпочтение** — направление, которое обозначено, но окончательно не выбрано.
- **Открытый вопрос** — решение, которое ещё не принято. Открытые вопросы не являются требованиями реализации.
- **Рабочая конкретизация** — явно обозначенное допущение для проверяемой спецификации, которое не следует выдавать за отдельное подтверждение владельца.

Конкретные имена MCP-методов, схема SQL, алгоритмы анализа, протокол загрузки плагинов и точные параметры конфигурации пока не утверждены. Документ не выбирает их за владельца.

## 2. Назначение и исходная проблема

Система представляет собой постоянно работающий атлас кода: индекс сущностей и связей проекта, доступный нейросетевому агенту через MCP.

В текущем процессе агент собирает структуру проекта многочисленными текстовыми поисками, затем исследует другие участки и перепроверяет связи. Это происходит в том числе внутри одной сессии. По оценке владельца, начальное исследование может расходовать около полумиллиона токенов. Это исходное наблюдение, а не установленный результат измерений или целевой показатель производительности.

У проекта уже есть описательная карта кода. Требуется более подробное представление, позволяющее переходить от конкретной переменной или метода к окружению, владельцу, вызывающему коду и используемой реализации.

### 2.1. Цели

| ID | Требование |
| --- | --- |
| G-01 | Хранить структурированную информацию о коде и его связях для использования агентом. |
| G-02 | Сокращать необходимость повторно восстанавливать связи текстовым поиском. |
| G-03 | Давать контекст вокруг запрошенной сущности, чтобы агент видел механизм её работы. |
| G-04 | Позволять отличать одноимённые методы разных классов и разбирать вызовы через интерфейсы. |
| G-05 | Поддерживать исправление данных агентом и проверку исправлений разработчиком. |
| G-06 | Строить подробную память о коде, даже если часть накопленной информации пока не используется запросами. |
| G-07 | Наглядно показывать в веб-интерфейсе, какие данные полученного графа использовались и как часто. |

### 2.2. Показательный случай: платёжная система

В проекте существуют старая и новая реализации платёжной системы, использующие один интерфейс. Старая реализация сохранена в коде, но отключена. Текстовое совпадение имени метода или обращение через интерфейс не должно само по себе означать, что используется старая реализация.

Атлас должен помогать установить, к какой реализации относится исследуемый вызов и как он связан с окружающим кодом. Способ установления активной реализации и поведение при невозможности однозначного вывода пока не выбраны.

## 3. Развёртывание и хранение

### 3.1. Состав контейнера

| ID | Требование |
| --- | --- |
| D-01 | Система развёртывается в отдельном Docker-контейнере с доступом к папке проекта. |
| D-02 | Основой служит контейнер PostgreSQL, в который добавляется бинарник Atlas с нативными плагинами. Интерпретаторы и toolchain анализируемых языков не устанавливаются. |
| D-03 | В PostgreSQL устанавливается pgvector. |
| D-04 | Данные атласа хранятся в PostgreSQL с индексами. |
| D-05 | Система предоставляет MCP-доступ и веб-интерфейс на порту для проверки исправлений и аналитики использования графа. |
| D-06 | Настройки приложения задаются через переменные окружения (ENV), передаваемые контейнеру в docker-compose. |
| D-07 | Atlas поставляется готовым Docker-образом: владелец собирает и выполняет docker push, получатель добавляет image-сервис в Compose своего проекта без checkout и сборки Atlas. |

**Предпочтение:** бинарник приложения, вероятнее всего, будет написан на Rust либо сопоставимом языке. Окончательного выбора языка нет.

Наличие pgvector не означает обязательного использования векторного поиска или генерации эмбеддингов. Решение о его применении отложено; допустим вариант, в котором расширение не используется.

Способ сохранения данных БД при замене контейнера, права доступа к папке проекта, номера портов и управление процессами внутри контейнера не определены.

Готовый образ публикуется в указанном владельцем Docker Hub-репозитории `drlenux/memory-tools`. Тег выбирается для выпуска; наличие адреса не означает факта публикации. Compose получателя задаёт доступ к своему коду и отдельное хранение БД Atlas.

### 3.2. Транзакции

Все обновления данных выполняются через транзакции. Успешное обновление фиксируется через `commit`; при ошибке незавершённая транзакция не должна оставлять частично применённое обновление и подлежит откату.

Это относится как к обновлениям анализатора, так и к исправлениям агента и решениям разработчика. Границы транзакции — отдельный объект, файл или группа изменений — ещё не определены. Конкретный набор индексов БД также не выбран.

### 3.3. Конфигурация через ENV в docker-compose

Конфигурация приложения задаётся переменными окружения, передаваемыми контейнеру через `docker-compose.yml`. Все предусмотренные настройки приложения должны быть доступны таким способом, включая директории наблюдения, исключения, задержку переиндексации, выбор языковых и фреймворковых плагинов и настройки ограничения ресурсов.

При запуске приложение использует переданные ENV. Для изменения настроек не требуется править исходный код, пересобирать образ или вручную редактировать конфигурационные файлы внутри контейнера. Новые значения применяются при запуске контейнера с обновлённым окружением.

Имена переменных, форматы списков и типов, единицы измерения, обязательные значения, значения по умолчанию и реакция на некорректный ENV определяются при техническом дизайне. Механизм применения ограничений CPU/RAM и их область действия остаются открытыми; наличие ENV само по себе не определяет способ ограничения ресурсов контейнера.

## 4. Графовая модель

### 4.1. Общий принцип

Код представляется графом сущностей и типизированных связей. Единственная общая верхняя вершина не требуется. Исследование может начинаться снизу: от переменной к методу, затем к классу и вызывающему коду.

Отношения «принадлежит», «вызывает» и другие описываются рёбрами. Ранее обсуждавшийся вариант отдельных вершин отношений с enum отменён.

Граф — логическая модель. Его физическое представление в таблицах PostgreSQL не определено. Использование специальной графовой БД не согласовано.

### 4.2. Сущности

| Сущность | Требуемая информация |
| --- | --- |
| Переменная | Какая это переменная, её тип и сведения о присвоенном значении или выражении; место нахождения; область использования, включая диапазон строк. |
| Функция | Сама функция, её расположение и сведения обо всех возвратах. |
| Метод | Сам метод, его расположение, сведения обо всех возвратах и связи с классами и вызывающим кодом. |
| Класс | Сам класс и связи, позволяющие рассматривать его методы, наследование и использование. |

У каждой вершины есть уровень доверия. Для рёбер уровень доверия также хранится отдельно: доверие к вершине не заменяет доверие к связи.

Интерфейсы, трейты и их участие в связях необходимо учитывать при анализе PHP. Их точное представление, а также необходимость отдельных вершин для вызовов, присваиваний и выражений не утверждены.

### 4.3. Связи

Нужно различать как минимум принадлежность и вызов. Нельзя считать связь между методом и классом доказательством вызова метода.

Граф должен позволять отвечать на вопросы:

- В каком методе находится переменная?
- Какому классу принадлежит метод и через какие классы он доступен?
- Кто вызывает метод и сколько ссылок или вызовов с ним связано?
- Какая реализация используется в исследуемом месте?
- Какие отношения связаны с наследованием, использованием трейта или переопределением?

Полный перечень типов рёбер, направления связей и способ подсчёта ссылок пока не определены.

### 4.4. Переменные и изменение значений

Для переменной нужно хранить сведения о типе, присваивании и области использования. История изменения исходного кода описана отдельно в разделе 6.

Полный анализ движения значений по всем присваиваниям и веткам внутри метода не утверждён. Последнее уточнение владельца конкретизировало историю по Git и анализ условий возврата. Оно не закрепляет автоматически отдельные вершины для каждого присваивания или полную модель потока данных.

## 5. Методы, функции и возвраты

### 5.1. Несколько вариантов возврата

Вершина метода или функции содержит информацию обо всех находящихся в ней `return`. Нельзя сводить описание к одному возврату или одному общему типу, теряя отдельные случаи.

Система должна учитывать legacy-код, в котором один метод в разных обстоятельствах возвращает `null`, целое число, строку, объект, ресурс или другие значения.

| ID | Требование к каждому возврату |
| --- | --- |
| R-01 | Указать расположение, включая строку `return`. |
| R-02 | Сохранить возвращаемое выражение или сведения о возвращаемом значении. |
| R-03 | Указать тип возвращаемого значения для этого случая. |
| R-04 | Показать, при каком условии происходит этот возврат, включая относящиеся к нему ветвления `if`. |
| R-05 | Хранить небольшой фрагмент исходного кода вокруг `return`: ориентировочно две-три строки выше и ниже. |
| R-06 | Дать возможность увидеть, откуда берётся возвращаемое значение, без обязательного дополнительного текстового поиска. |

### 5.2. Граница уточнения

Небольшой фрагмент вокруг `return` может не включать источник значения, если тот расположен значительно выше или в другом методе. Требование видеть происхождение значения зафиксировано, но способ расширения контекста в таком случае пока не выбран.

Не определены формат условий возврата, представление неизвестного типа и правила для неявного завершения функции без `return`. Обработка иных способов выхода, например исключений, отдельно не обсуждалась.

## 6. История по Git

### 6.1. Требуемые сведения

Для исследуемого участка кода требуется связь с изменениями в Git. Агент должен получать хеш и название или сообщение коммита, чтобы при необходимости самостоятельно запросить более подробную информацию.

| ID | Требование |
| --- | --- |
| H-01 | Показывать как минимум последнее изменение исследуемой строки или участка по Git. |
| H-02 | Позволять увидеть предыдущее и текущее содержимое. |
| H-03 | Различать добавление нового кода и изменение существовавшего кода. |
| H-04 | Включать контекст выше и ниже изменённого участка. |
| H-05 | Позволять увидеть более широкую правку, когда переписан весь метод, а не только одна строка. |
| H-06 | Предоставлять хеш и название или сообщение соответствующего коммита. |

Название ветки не закреплено как обязательный атрибут происхождения строки. Требование к коммиту сформулировано через его хеш и сообщение.

### 6.2. Границы решения

Полная история всех версий не является подтверждённым требованием. Минимально запрошена последняя правка с предшествующим состоянием и контекстом.

Конкретные Git-команды, алгоритм сопоставления строк после перемещения или переработки, объём контекста и способ хранения истории не выбраны. Отдельно нужно определить отображение незакоммиченных изменений.

История исходного кода по Git и исправление знаний атласа агентом — разные операции. MCP-исправление относится к данным атласа; изменение исходных файлов этим методом не запрошено.

## 7. Наблюдение за проектом и индексация

### 7.1. Автоматическое обновление

Система постоянно работает и отслеживает изменения файлов в выбранных директориях проекта. Изменившиеся файлы направляются на переиндексацию.

Наблюдение должно быть ограничено кодом и нужными директориями. Служебные директории, включая `.git` и каталоги инструментов агента, не должны индексироваться как исходный код. Точный список включений и исключений ещё не задан.

Использование метаданных Git для истории требуется независимо от исключения `.git` из индекса исходного кода.

### 7.2. Задержка обработки

Нужна настраиваемая задержка перед обновлением, чтобы переиндексация не запускалась немедленно во время серии правок. Ориентир из обсуждения — около пяти секунд.

Пять секунд не установлены как обязательное фиксированное значение. Нужно отдельно определить, отсчитывается ли задержка от последнего изменения, первого события или очередного цикла обработки.

### 7.3. Проверка PHP

Уточнение версии 0.4 заменяет ранее обсуждавшийся внешний `php -l` встроенным разбором языка. Для анализа PHP не требуется PHP CLI. Ошибка разбора не должна восприниматься как удаление существующего кода; файл получает диагностику. Точные границы распознаваемого синтаксиса документируются у языкового плагина.

### 7.4. Ресурсы

Должны настраиваться допустимое использование процессорных ресурсов и оперативной памяти. В обсуждении обозначены процессорное время либо число доступных ядер; конкретная форма ограничения не выбрана.

| Настройка | Статус |
| --- | --- |
| Директории проекта, за которыми ведётся наблюдение | Требуется; формат не определён. |
| Исключения из индексации | Требуются; полный список не определён. |
| Задержка перед переиндексацией | Требуется; ориентир — около пяти секунд. |
| Ограничение CPU | Требуется; единицы и механизм не определены. |
| Ограничение RAM | Требуется; величина и механизм не определены. |
| Проверка разбора языка | Встроена в языковой плагин, без запуска интерпретатора. |

Не определены численные лимиты, поведение при их достижении и то, распространяются ли они на приложение отдельно или на весь контейнер вместе с PostgreSQL.

## 8. Плагинная архитектура

Механизм анализа должен поддерживать нативные плагины, расширяющие возможности бинарника Atlas. Языковой плагин обучает анализатор работе с указанным языком; он не должен быть написан на этом языке и требовать его runtime. После PHP планируется добавлять JavaScript, Go, Rust и Python через тот же контракт. Фреймворковый плагин — отдельное расширение языкового анализа.

### 8.1. Плагин PHP

Первый нативный плагин отвечает за PHP как язык программирования и исполняется внутри Atlas без PHP CLI и Composer. Нужно учитывать его объектную модель и обсуждённые случаи:

- классы и методы;
- интерфейсы и разные реализации одного интерфейса;
- наследование;
- методы из трейтов;
- переопределение методов;
- вызов родительской реализации через `parent`, в том числе в конструкторах;
- переменные, типы, возвраты и относящиеся к ним условия;
- магические методы и свойства.

Метод, объявленный в трейте или родителе, может быть доступен через несколько классов. Атлас должен учитывать это и переопределения. Наличие переопределения само по себе не равно вызову родительского метода; фактический вызов `parent` должен учитываться отдельно как вызов.

Конкретный парсер или готовый анализатор, версия PHP и точные границы поддержки языковых конструкций не выбраны.

### 8.2. Плагин Yii 2

Второй, отдельно регистрируемый плагин отвечает за Yii 2 и расширяет анализ PHP сведениями о механизмах фреймворка, в том числе магических свойствах и методах. Он должен помогать раскрывать, как эти обращения работают.

Нужная реализация может находиться глубоко в `vendor`, а не в файлах приложения. Система должна учитывать этот источник информации. Обязательное полное индексирование всего `vendor`, компактный индекс зависимостей и разбор по запросу — возможные варианты, но ни один из них пока не выбран.

Перечень поддерживаемых механизмов Yii 2 и технический контракт взаимодействия двух плагинов остаются открытыми.

## 9. MCP и выдача контекста

### 9.1. Обязательные возможности

| Возможность | Ожидаемое поведение |
| --- | --- |
| Получение данных | Агент запрашивает информацию о коде и получает соответствующий участок атласа с окружением. |
| Исправление ошибочных данных | Агент сообщает, что имеющиеся сведения ошибочны, и корректирует существующую вершину или связь в рамках правил доверия. |
| Автоматическое обновление | Индекс изменяется по результатам наблюдения и анализа файлов без необходимости ручного запуска каждого обновления. |

Автоматическое обновление является поведением системы. Отдельный MCP-метод принудительного запуска переиндексации не был явно запрошен.

### 9.2. Содержимое ответа

Ответ должен включать больше, чем изолированную запрошенную сущность. Нужен связный участок карты, позволяющий увидеть, в каком окружении она работает, кому принадлежит и кто её вызывает.

В зависимости от запроса это включает связанные вершины и рёбра, сведения о ссылках, соответствующие возвраты с кодом и данные Git. Уровни доверия должны быть доступны вместе с относящимися к ним вершинами и связями, чтобы различать результат анализатора, исправление агента и подтверждение разработчика.

Цель — избежать необходимости многократно обращаться к MCP только для восстановления ближайшего контекста и проверки того, что речь идёт о нужном методе.

Конкретный формат передачи графа, размер ответа, глубина обхода и порядок включения соседних сущностей не заданы. Обязательная графическая визуализация всего атласа не установлена: пользователь описывал прежде всего граф связей для нейронки.

## 10. Уровни доверия и полномочия

### 10.1. Три уровня

| Уровень | Источник | Значение |
| --- | --- | --- |
| 1 | Анализатор | Автоматически выведенные данные; самый низкий приоритет. |
| 2 | Нейросетевой агент | Исправленные агентом данные. Используются как действующая истина сразу, до решения разработчика. |
| 3 | Разработчик | Подтверждённая разработчиком истина; наивысший приоритет. |

Уровень доверия задаётся для вершины и для ребра. Это приоритет источника данных, а не согласованная численная оценка вероятности правильности вывода.

### 10.2. Создание, изменение и удаление

| Операция | Анализатор | Агент | Разработчик |
| --- | --- | --- | --- |
| Создать вершину или ребро | Да | Нет | Нет |
| Обновить существующие данные | Да, с ограничением по доверию | Да, с ограничением по доверию | В рамках проверки исправлений агента |
| Удалить вершину или ребро | Да | Нет | Нет |

Разработчик работает с тем, что объявил или исправил агент. Произвольное создание сущностей через веб-интерфейс не входит в согласованную модель.

### 10.3. Правило обновления

Обновление от источника с более низким уровнем доверия не должно перезаписывать данные более высокого уровня:

- анализатор уровня 1 не перезаписывает исправление уровня 2;
- анализатор уровня 1 не перезаписывает подтверждение уровня 3;
- агент уровня 2 не перезаписывает подтверждение уровня 3.

Следовательно, обычная повторная индексация не отменяет исправление агента только потому, что анализатор снова получил прежний результат.

Проверка уровня применяется именно к обновлению. Для создания и удаления проверка уровня доверия не требуется, но ограничение исполнителя сохраняется: эти операции выполняет только анализатор.

Порядок конкурирующих обновлений одного уровня, включая повторные исправления разными агентами, пока не определён.

### 10.4. Удаление выше доверия

Если соответствующая строка исходного кода полностью удалена, анализатор может удалить связанную с ней сущность независимо от уровня доверия. Уровни 2 и 3 не защищают объект от удаления вместе с исходным кодом.

Это правило не означает, что низкий уровень доверия разрешает обычное изменение подтверждённых данных. Основанием исключения является удаление исходного кода.

Как отличать удаление от перемещения, изменения строки или переписывания метода, ещё не решено. Это существенно: ошибочное признание изменённого объекта удалённым может обойти защиту доверия. Метод сопоставления сущностей между версиями должен быть согласован до реализации данного правила.

## 11. Веб-интерфейс проверки

Нужен веб-интерфейс, доступный на порту, в котором разработчик видит все вершины и рёбра с уровнем доверия 2 и исправления, внесённые агентом.

### 11.1. Решения разработчика

| Действие | Результат |
| --- | --- |
| Нет решения | Исправление агента продолжает действовать как истина уровня 2. |
| `approve` | Исправление подтверждается; уровень доверия повышается до 3. |
| `decline` | Исправление агента отменяется. |

Проверка человеком не является предварительным условием применения исправления агента.

Для просмотра и отмены правки система должна сохранять достаточно сведений о ней и предшествующем состоянии. Конкретная модель хранения этих сведений не утверждена; это не устанавливает отдельное требование к бессрочному журналу всех изменений.

### 11.2. Нерешённая семантика `decline`

Согласовано именно действие «отменить исправление нейронки». Пока не определено:

- восстанавливается ли значение до исправления или последний результат анализатора;
- какой уровень доверия получает восстановленное значение;
- как отменяется последняя правка, если было несколько последовательных исправлений;
- разрешается ли агенту повторить ранее отклонённое исправление;
- может ли разработчик ввести свой вариант значения вместо `approve` или `decline`.

До выбора этих правил нельзя считать, что `decline` автоматически означает переход к уровню 1 либо подтверждение альтернативы на уровне 3.

Сценарии ниже выражают уже сформулированные требования. Они не задают новый набор технологий или алгоритмов.

| № | Ситуация | Ожидаемое поведение |

| 1 | У двух классов есть одноимённые методы. | Ответ позволяет различить методы и их окружение. |
| 2 | Старая и новая платёжные реализации используют общий интерфейс. | Наличие старой реализации не выдаётся за факт её использования только из-за общего интерфейса или имени метода. |
| 3 | Один метод возвращает разные типы из разных ветвей. | Видны отдельные `return`, строки, типы, условия и фрагменты кода. |
| 4 | Метод доступен через трейт или наследование и переопределён в части классов. | Атлас учитывает различия реализаций и доступности метода. |

| 7 | Код изменён несколько раз подряд. | Переиндексация учитывает настроенную задержку; точное правило отсчёта выбирается отдельно. |
| 8 | Встроенный PHP-плагин обнаружил ошибку разбора файла. | Файл получает диагностику; неуспешный разбор не разрешает удаление прежних сведений. |
| 9 | Транзакция обновления завершается ошибкой. | Частично применённые изменения этой транзакции не становятся итоговым состоянием. |
| 10 | Агент исправил данные уровня 1. | Исправление получает уровень 2 и действует до решения разработчика. |
| 11 | Анализатор повторно получил значение, противоречащее уровню 2 или 3. | Защищённые данные не перезаписываются. |
| 12 | Разработчик нажал `approve`. | Соответствующие исправленные данные получают уровень 3. |
| 13 | Агент пытается изменить данные уровня 3. | Обновление более низкого уровня не перезаписывает их. |
| 14 | Разработчик нажал `decline`. | Исправление агента отменяется; точное восстановление определяется после решения вопросов раздела 11.2. |
| 15 | Исходная строка действительно удалена. | Анализатор может удалить связанную сущность независимо от доверия. |
| 16 | Агент или разработчик пытается создать либо удалить объект атласа. | Операция не разрешена: создание и удаление принадлежат анализатору. |
| 17 | В Git строка добавлена впервые либо изменена. | Представление истории позволяет различить случаи и посмотреть контекст. |
| 18 | Полученные участки графа содержат разные вершины и рёбра. | В веб-аналитике можно различить эти элементы и увидеть частоту их использования по явно названной метрике. |
| 19 | Один и тот же элемент присутствует в нескольких выданных MCP-ответах. | При рабочей метрике выдачи видна частота включения элемента в ответы; она не называется доказанным использованием агентом. |
| 20 | Пользователь выбирает период аналитики. | Сводка, наглядное представление и детализация относятся к одному указанному периоду. |
| 21 | В docker-compose заданы ENV с настройками приложения. | При запуске приложение использует переданные настройки без ручной правки файлов внутри контейнера. |
| 22 | Контейнер запускается с изменёнными ENV и прежним образом. | Приложение использует новые значения без изменения исходного кода и пересборки образа. |

Целевые показатели по расходу токенов, времени ответа, скорости индексации и размеру БД пока не установлены.

## 14. Что не закреплено как обязательное требование

Следующие идеи ранее предлагались ассистентом, но не были явно приняты владельцем; они не включены в обязательный объём:

- сохранение последнего успешного индекса при ошибке разбора;
- отдельные состояния актуальности и признаки неполноты ответа;
- приоритет запросов над фоновыми задачами;
- отдельный режим объяснения и доказательств каждой связи;
- отдельная вершина для каждого присваивания и каждого вызова;
- конкретная стратегия компактного индексирования `vendor`;
- выбор готового анализатора и конкретных команд извлечения истории Git;
- обязательный векторный поиск, эмбеддинги или иной сценарий использования pgvector.

Ранее предложенная модель вершин отношений прямо заменена типизированными рёбрами. Rust остаётся предпочтением. Обязательная транзакционность, напротив, подтверждена владельцем и включена в требования.

## 15. Подходы к реализации

Владелец установил следующий порядок приоритетов; все перечисленные подходы применяются совместно:

1. **Design architecture first.** Сначала проектируется архитектура: границы компонентов, обязанности, зависимости, потоки данных и контракты. Затем реализуется поведение в этих границах.
2. **Design patterns.** Паттерны проектирования выбираются под конкретные задачи архитектуры с объяснением их назначения.
3. **TDD.** Работа над исполняемым поведением проходит цикл «падающий тест → минимальная реализация → рефакторинг». Сценарии OpenSpec служат основой поведенческих тестов.
4. **Service Layer.** Прикладные сценарии и их координация оформляются в слое сервисов. MCP и веб-интерфейс обращаются к этому слою; прикладные правила не дублируются в обработчиках входных запросов.
5. **SOLID + DRY + KISS + YAGNI.** Ответственности и зависимости разделяются, общие правила не дублируются, решения остаются простыми и отвечают текущим требованиям.
6. **Clean Simple Code.** Код должен быть понятным и простым: ясные имена, связные небольшие операции и читаемый поток управления.

Порядок задаёт приоритеты при проектировании. Он не выбирает конкретные паттерны, язык, библиотеки или контракт плагинов. Рабочие правила закреплены также в [AGENTS.md](AGENTS.md).

## 16. Веб-аналитика использования графа

### 16.1. Назначение

Дополнительное требование владельца: в веб-интерфейсе нужна наглядная аналитика, показывающая, что из полученного графа использовалось и как часто. Это отдельная возможность наряду с проверкой исправлений.

### 16.2. Рабочая конкретизация метрик

До уточнения смысла «использовалось» базовыми наблюдаемыми событиями считаются успешная выдача контекста через MCP и включение конкретных вершин и рёбер в выданный ответ. Панель показывает число таких ответов и частоту выдачи каждого элемента; один элемент учитывается один раз в одном ответе. Включение в разные ответы считается отдельно.

Это рабочая конкретизация для спецификации, а не утверждение, что выдача доказывает последующее использование данных агентом. Для метрики использования в решении нужна отдельная обратная связь от агента; её обязательность и контракт пока не выбраны. Отсутствие такой обратной связи не означает нулевое фактическое использование.

### 16.3. Требования и представление

| ID | Требование | Статус |
| --- | --- | --- |
| A-01 | Веб-интерфейс предоставляет наглядную аналитику того, какие элементы полученного графа использовались и как часто. | Требование владельца. |
| A-02 | Метрика явно объясняет, какое событие учитывается; запрос, выдача и последующее использование агентом не смешиваются. | Уточнение измеримости A-01. |
